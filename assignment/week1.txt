Python's dynamic typing binds an identifier to an object on the heap rather than to a fixed memory location tied to a declared type. Each object carries its own type metadata and reference count within the CPython object header, so the interpreter checks operand types at runtime rather than during compilation. This contrasts with statically typed languages such as Java or C, where the compiler determines each variable's type and allocates a corresponding fixed-size stack slot before execution ever begins (see diagram above). Consequently, Python names can be reassigned to objects of any type without violating a fixed schema, which grants flexibility but requires the interpreter to repeatedly resolve types at runtime. Greenman et al. (2019) demonstrate that this runtime resolution imposes a measurable and quantifiable performance cost relative to compiled, statically typed code.
Regarding division, the / operator always performs true division and returns a float computed through IEEE-754 double-precision arithmetic, regardless of whether the operands were integers. The // operator performs floor division: it computes the quotient and rounds toward negative infinity, and when both operands are integers, the result remains an integer computed via exact integer arithmetic rather than floating-point approximation. This distinction matters because binary floating-point representation cannot exactly encode most decimal fractions, introducing small rounding errors that integer arithmetic avoids entirely.
A well-documented real-world consequence of this kind of floating-point imprecision is the 1991 Patriot missile failure, in which accumulated rounding error in a 24-bit time register caused a 0.34-second tracking drift, allowing an incoming Scud missile to go undetected and resulting in fatalities. Systems performing currency calculations or timing-critical operations therefore often prefer integer or floor-division arithmetic to avoid comparable cumulative errors.
Question 2
In Python, if A and B or C is parsed according to operator precedence, where and binds more tightly than or, so the expression is evaluated as (A and B) or C. Short-circuit evaluation means operands are computed left to right, and evaluation stops the moment the overall truth value is determined. If A is False, Python never evaluates B, since a false and clause is already determined regardless of B; it then proceeds to evaluate C because the or still needs a value. If A and B are both True, the or clause is already True, so C is skipped entirely (see diagram above).
This lazy-evaluation strategy avoids unnecessary computation, particularly when operands involve expensive function calls or I/O operations. Logothetis and Mishra (1981) formalized code-generation techniques that translate compound Boolean expressions into single-pass conditional jumps, eliminating redundant evaluation at the compiler level. To optimize execution speed, developers should order conditions so that the branch most likely to short-circuit runs first: for and chains, place cheap, likely-false checks first; for or chains, place cheap, likely-true checks first.
This principle has tangible real-world impact in large-scale web systems. Authentication routines commonly write conditions like if cached_token_valid() or expensive_database_lookup(), ordering the inexpensive cache check before the costly database query. Applied across millions of requests per day, correctly ordered short-circuit conditions meaningfully reduce server load, latency, and infrastructure cost.
